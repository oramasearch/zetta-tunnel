# zetta-tunnel v0.1.0

**Released 2026-10-15. The first release.** One binary, `zetta-tunnel`, and one private image,
`docker.io/oramasearch/zetta-tunnel:v0.1.0`. It carries Orama's network layer for Lake and the Orama
operator: developer tunnels, egress by DNS name, peer gateways, the ingress gateway and the mesh node
agent, all over one mutual TLS 1.3 transport. Proprietary to Orama; private repository and image.

How the roles fit together, and with Lake and the operator: [`docs/architecture.md`](../architecture.md).

## What it includes

Every role in the binary and the image, each with its contract:

| Role | What it does | Contract |
|---|---|---|
| `client` | A developer's machine: a loopback listener whose connections go to the relay over mutual TLS with the developer's grant certificate | [client](../client.md), [tunnel](../tunnel.md) |
| `relay` | One per cluster: authenticates grant certificates against the projected grants file and the customers' CA bundle, and forwards each connection to that grant's endpoint. Live revocation and expiry close a grant's sessions | [relay](../relay.md), [tunnel](../tunnel.md) |
| `endpoint` | One per grant, in the workspace: forwards relay connections to one fixed target | [endpoint](../endpoint.md) |
| `egress` | Outbound by DNS name: authorizes the workload's source address, the exact name and the port before resolving; HTTPS by SNI, other TCP by the `ZTEG1` preface. Never accepts an address from the workload | [egress](../egress.md) |
| `peer` | Named services between clusters or networks over mutual TLS, never routed addresses; works with identical private addresses at both sites | [peer](../peer.md) |
| `ingress` | Public TLS from cert-manager's certificates, host and path routing to Services, HTTP/1.1, HTTP/2, WebSockets, unbuffered streaming, body limits, reloads, probes and metrics | [ingress](../ingress.md) |
| `mesh` | Per-node agent: fail-closed nftables capture inside each enrolled pod's network namespace, exact workload identities over mutual TLS, Cilium still the enforcer. Linux only; the one privileged role | [mesh](../mesh.md) |

Under every role:

- **Transport** (`zetta_tunnel_transport`): mutual TLS 1.3 only, over Corosio's OpenSSL provider; a
  peer certificate is always required, the expected identity is matched against its SANs, and there
  is no plaintext fallback. [transport](../transport.md)
- **Projected configuration**: each role reads one file (grants, rules, peers, routes, mesh
  projection) and its certificates, written by the operator, reloaded on change or `SIGHUP`. No role
  calls Lake or the Kubernetes API.
- **Audit**: every role writes an allow or deny record per connection as JSON lines.
- **The image**: `scratch` plus the fully static `linux/amd64` binary, non-root (`65532:65532`)
  except the mesh agent, no shell or package manager. [image](../image.md)
- **Portable tunnel clients** (`tools/build-clients.sh`, `ZETTA_TUNNEL_PORTABLE`):
  `zetta-tunnel-darwin-arm64` (OpenSSL and nghttp2 linked in; loads only the system's `libc++` and
  `libSystem`) and `zetta-tunnel-linux-amd64` (fully static), published with `SHA256SUMS` as the
  private image `oramasearch/zetta-tunnel-clients`, which Lake serves to developers (lake#745).
- **Install**: `sudo cmake --install build` installs `bin/zetta-tunnel` only; an in-source build is
  refused. With no arguments it prints its usage, and a failure names what failed.
- **Licences**: only permissive dependencies are linked. [licences](../licences.md)

## What it does not include

- Tunnel clients for macOS on Intel, Linux arm64 and Windows.
- Delivery of the audit records into the workspace Zetta: they are written as JSON lines today
  (zetta#1281).
- Usage records with byte counts per session, and common metrics in every role
  (zetta-tunnel#18).
- QUIC: the transport is TLS 1.3 over TCP only.

## Known issues

Security-relevant first.

1. **The relay sees a tunnel's plaintext.** Both hops are mutual TLS, but the relay terminates them
   ([tunnel](../tunnel.md)). Run application TLS inside the tunnel (Postgres TLS, HTTPS) where the
   relay must not see the bytes.
2. **The macOS client is not signed or notarized.** Downloaded through a browser it is quarantined by
   Gatekeeper; fetched with `curl` it is not.
3. **Mesh enrolment is not usable on real workspaces yet.** Capture would refuse kubelet probes and
   platform peers that are not in the mesh, and there is no startup gate (orama-operator#474); the
   agent runs on every node with nothing enrolled.
4. **The relay's address changes** when its last grant ends and a new one starts, because the operator
   removes and recreates its LoadBalancer (orama-operator#507).
5. **The ingress gateway is not yet compared with ingress-nginx under load on a cluster**, and no
   cluster has cut over to it (orama-operator#473).
6. A failure caused by an unreadable or invalid certificate file reports `TLS configuration failed`
   without naming the file.

## Where it has run

On the management cluster `orama-production-cluster-01` (the development environment), deployed by
the Orama operator, before this release under the tags `dev-933d6fc` and `dev-00be276` (the same
code as this release's roles):

- the relay (two replicas behind a LoadBalancer on 443) and one endpoint per grant: Steve connected
  `psql` from his Mac to a workspace Postgres through a tunnel on 2026-10-14, and a SQLite service
  after operator#509;
- the egress gateway in a workspace: an allowed name answered 200 and an undeclared one was refused;
- the mesh agent's privileged Linux proof on an AKS node (`tools/prove-mesh-linux.sh`).
