# zetta-tunnel v0.2.0

**Released 2026-11-02.** Four security fixes from Lake's pre-launch security review
([orama-bridge#223](https://github.com/oramasearch/orama-bridge/issues/223)) and the peer fix that lets
the observability hub read distant clusters. Same binary and private image,
`docker.io/oramasearch/zetta-tunnel:v0.2.0`; every role of [v0.1.0](v0.1.0.md) is unchanged unless
listed here.

> **Two contracts change in a way the operator must follow.** A relay of this release refuses the
> grants file the operator writes today, and the mesh agent refuses today's workload projection. Both
> fail closed. Before a cluster with a tunnel grant or an enrolled mesh workload runs this image, the
> operator must ship
> [orama-operator#844](https://github.com/oramasearch/orama-operator/issues/844) (grants) and
> [orama-operator#869](https://github.com/oramasearch/orama-operator/issues/869) (mesh). On
> 2026-11-02 no cluster has either, so the image can roll for the peer fix now.

## What it includes

| Change | Roles | Pull request |
|---|---|---|
| **Each tunnel grant is bound to its customer CA** (LSR-074). A grant now lists `client_ca_sha256`, the SHA-256 fingerprints of the CA certificates allowed to sign for it (1 to 16, lowercase hex, required). A certificate from any other customer's CA is refused with the new audit reason `grant_issuer`, before any endpoint is contacted. Before, the relay trusted every CA in its bundle for every grant | relay | [#35](https://github.com/oramasearch/zetta-tunnel/pull/35) |
| **Unauthenticated sockets no longer use the session budget** (LSR-179). Pending connections have their own budget, `--max-pending-sessions` (default 128) and `--max-pending-per-source` (default 32), with a setup deadline counted from acceptance; `--max-sessions` counts authorized sessions only. Public ingress also bounds connections (`--max-sessions-per-source`) and HTTP/1 and HTTP/2 requests (`--max-requests-per-source`) per source, by default a quarter of its total and at least 4. TLS contexts are cached and refreshed at startup, every two seconds and on `SIGHUP`; invalid credentials fail readiness and refuse new traffic | relay, endpoint, peer, ingress, egress | [#36](https://github.com/oramasearch/zetta-tunnel/pull/36) |
| **The DNS egress gateway checks every resolved address** (LSR-263). One private, loopback, link-local or metadata, CGNAT, documentation, multicast or Azure platform address (`168.63.129.16`) in an answer, including IPv4-mapped and 6to4 forms, refuses the lookup with `destination_forbidden`; IPv6 must be global unicast. The gateway connects to the checked numeric addresses, so a DNS change after the check is not followed. A new optional per-rule `denied_cidrs` takes further exclusions | egress | [#38](https://github.com/oramasearch/zetta-tunnel/pull/38) |
| **The mesh agent pins each workload's network namespace** (LSR-264). A workload projection now requires `pod_uid` and `network_namespace_inode`. The agent opens the process directory once, checks the pod's cgroup before and after opening `ns/net`, verifies the inode and namespace type, and keeps that handle for the workload's runtime, so a reused PID cannot move an identity into another pod's namespace | mesh | [#39](https://github.com/oramasearch/zetta-tunnel/pull/39) |
| **A peer's setup deadline starts when its connection is accepted.** It used to start when the gateway began waiting, so on an idle listener a connection arrived already late and was closed within 100 ms; only a nearby cluster connected. The audit record's `started_at` and the health probe's deadline also start at acceptance. This is why the production hub could not read `orama-production-cluster-02`'s and nonprod's metrics ([#40](https://github.com/oramasearch/zetta-tunnel/issues/40), [orama-operator#1111](https://github.com/oramasearch/orama-operator/issues/1111)) | peer | [#41](https://github.com/oramasearch/zetta-tunnel/pull/41) |

Issues closed by these: [#28](https://github.com/oramasearch/zetta-tunnel/issues/28),

## Upgrading

- **Relay:** every grant needs `client_ca_sha256`; a snapshot with one grant missing it is refused
  whole. The operator computes it from the `ZettaTunnel`'s `spec.clientCAPEM`
  ([orama-operator#844](https://github.com/oramasearch/orama-operator/issues/844)). An older relay
  refuses the five-field grants, so the relay and the operator change roll together.
- **Mesh:** every workload needs `pod_uid` and `network_namespace_inode`
  ([orama-operator#869](https://github.com/oramasearch/orama-operator/issues/869)). An agent with no
  enrolled workloads is unaffected.
- **Egress:** a DNS rule whose name resolves to a private or special-use address now fails. Cluster
  ranges in public address space are not in the built-in list; the operator projecting them into
  `denied_cidrs` is [orama-operator#1136](https://github.com/oramasearch/orama-operator/issues/1136).
  NetworkPolicy remains the second layer.
- **Capacity flags:** `--max-sessions` now counts authorized sessions. The new pending flags have
  defaults, so no flag is required.

## What it does not include

Everything v0.1.0 listed is still not included: tunnel clients for macOS on Intel, Linux arm64 and
Windows; audit delivery into the workspace Zetta (zetta#1281); usage records and common metrics
(zetta-tunnel#18); QUIC.

## Known issues

Security-relevant first.

1. **Until orama-operator#844 and #869 ship, a cluster running this image refuses every tunnel
   grant and every enrolled mesh workload** (fail closed, above).
2. **Cluster addresses in public space rely on NetworkPolicy alone** for DNS egress until
   orama-operator#1136.
3. **The relay sees a tunnel's plaintext** (as in v0.1.0): run application TLS inside the tunnel
   where the relay must not see the bytes.
4. **Per-source limits share one quota behind a NAT or proxy** that hides client addresses. The
   operator's relay, ingress and peer Services keep client addresses (`externalTrafficPolicy: Local`).
5. **The macOS client is not signed or notarized.**
6. **Mesh enrolment is not usable on real workspaces yet** (orama-operator#474), and the privileged
   mesh proof (`mesh_linux_fail_closed`) has not been rerun for #39 on a node.
7. **The relay's address changes** when its last grant ends (orama-operator#507).
8. **The ingress gateway is not compared with ingress-nginx under load** (orama-operator#473).

Before this release, only in tests. On 2026-11-02 the managing cluster `orama-production-cluster-01`
runs v0.1.0 (`main-9cd11b4`) as six peer gateways (the observability hub's links to the other three
