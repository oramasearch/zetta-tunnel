# Tunnel verification

Build prerequisites are C++26/Clang, CMake, Ninja, OpenSSL 3, nlohmann/json 3.12 and Python 3
(standard library only). On macOS, `brew install llvm cmake ninja openssl@3 nlohmann-json python`
provides them. Install the equivalent development packages on Linux; on Windows use a C++26
Clang toolchain and CMake packages for OpenSSL/nlohmann-json. The binary also contains egress,
peer and ingress roles; ingress adds pkg-config and libnghttp2 >= 1.61
(see [ingress verification](../ingress/testing.md)).

```sh
git submodule update --init --recursive
cmake -S . -B build -G Ninja
cmake --build build -j 6
ctest --test-dir build --output-on-failure
cmake -S . -B build-shared -G Ninja -DBUILD_SHARED_LIBS=ON
cmake --build build-shared -j 6
ctest --test-dir build-shared --output-on-failure
```

`tests/tunnel_integration.py` launches the actual binary in all three roles, using throwaway
Ed25519 CAs and certificates generated by `tunnel_certificates`. Its local TCP targets are
independent of the C++ forwarding implementation. Certificates include subject/authority key
identifiers for strict validation, including Python 3.14 clients. Fixtures live inside the build directory.
The configuration test rejects malformed dates, addresses, JSON, duplicate keys/IDs, oversized
files, grants without valid, distinct `client_ca_sha256` fingerprints and unsafe/invalid CLI flags.
The harness gives the relay the union of two customer CAs, as the operator does. `.clang-format` defines the repository's C++ formatting.

The integration cases prove concurrent binary forwarding and matching audit byte counts; grant
removal cutting an idle live session and refusing a new one; expiry cutting a live session;
expired, untrusted, missing-URI, ambiguous-URI, unknown-grant and overlong certificates being
refused; a certificate from another customer's CA, trusted by the relay and naming the grant and
its expiry, being refused with `grant_issuer` (`tunnel_other_customer_ca`, LSR-074); certificate expiry bounded by grant expiry; wrong relay/endpoint DNS identities being
refused; destination-shaped payloads reaching only the configured target; invalid reload clearing
authorization and readiness with later recovery; SIGHUP forcing a same-mtime reload; and capacity
limits while health probes remain responsive. Further cases cover missing certificates, TLS 1.2
refusal, developers attempting to bypass the relay, revocation under backpressure, stalled TLS
setup deadlines, projected-volume symlink rotation, missing grant files and changes to live grant
bindings. Copy loops yield after each buffer so continuous TLS traffic cannot starve cancellation.
Audit-sink failure must prevent forwarding and fail readiness; mismatched keys must fail startup.
The existing five transport tests remain enabled.

## Native PostgreSQL proof

Set `ZETTA_TUNNEL_PSQL` to `psql`'s absolute path and `ZETTA_TUNNEL_TEST_DATABASE` to a database
created for this run on the local `127.0.0.1:5432` server (role `stevesperandeo`, no password).
The suite's `tunnel_postgres` case runs a real query through client → relay → endpoint → Postgres,
then removes the grant during `pg_sleep` and requires psql to disconnect. No schema or user data
is changed. Without these two variables, only that optional environment-dependent case reports
Skipped; the TCP/TLS acceptance cases always run. The delivery proof sets both variables.

```sh
createdb -h 127.0.0.1 zetta_tunnel_issue3_proof_unique
export ZETTA_TUNNEL_PSQL=/absolute/path/to/psql
export ZETTA_TUNNEL_TEST_DATABASE=zetta_tunnel_issue3_proof_unique
ctest --test-dir build --output-on-failure
```

Choose a fresh name and only remove the database created by that invocation. No Docker is used.
Use the coordinator's Linux proof helper if available; otherwise record `Linux proof deferred`.
Windows source portability is maintained, but a native Windows proof requires a Windows runner.
